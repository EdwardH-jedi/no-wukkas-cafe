### Reproduction boundaries and minimum fixes

- **F1, two red tests:** Seed 3, Monday, real `startShift`, real pause-menu restart callback and real
  `stepRush` restart; change listening difficulty from Normal to Hard. Finish a headless run with the
  actual restarted seed/difficulty/week context. With only a weak Normal best, the report correctly says
  first score (`newBest=false`) but one `rush.end.newBest` line is emitted. With a strong Normal best and
  a weak Hard best, the report says `newBest=true` but no congratulations are emitted. Refresh the
  appropriate board's best on restart; merely ignoring a mismatched difficulty would still fail the
  second case. HUD construction is intercepted to obtain the production callback; audio/world are the
  existing harness doubles. This verifies line selection, not audible output or DOM activation.
- **F2, two red tests:** Parse version-1 JSON with (a) `grade: "constructor"` on an otherwise valid Monday
  entry, or (b) an Easy Excellent entry stored under `week:0:hard`. In (a), `in GRADE_RANK` succeeds through
  the prototype; comparisons produce `NaN` and a subsequent Excellent entry cannot displace the bad
  best. In (b), the legitimate Hard Good entry remains below the Easy result. Validate grade membership
  against actual enum values and enforce board/entry consistency. Discarding corrupt entries/boards is
  acceptable; re-homing a valid entry is also acceptable. The tests do not demand one recovery policy.
  The normal writer does not create these malformed inputs; this is the explicitly promised corrupt
  storage boundary, not a claim of remote compromise.
- **F3, one red test:** Write an Excellent score, construct a fresh store and successfully read it, then
  make the backend throw on reads. `read()` returns empty, `memoryOnly=true`; adding a Poor score makes
  Poor the best. Cache the last successful read before falling back. The original backend retains the
  Excellent score: this is session data loss, not demonstrated permanent disk deletion. Author tests
  cover failure from the first access and failed writes, but not failure after a successful reload.

Four green independent controls cover actual Day 2/week/Endless summary events through
`createRushFrame`: a score exists when the report callback runs, the next frame does not duplicate it,
and restarting clears the report note without deleting its score. The fourth covers disk round-trip,
